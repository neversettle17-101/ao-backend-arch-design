AO Backend Rewrite — Design & Implementation Plan

Replacing the current Next.js API routes + dual WebSocket servers with a single Go daemon serving REST, SSE event stream, terminal WebSocket, and the frontend bundle on one port. Covers design decisions, route surface, and the phased implementation plan.

Status: Design + implementation plan ready Frontend: TypeScript / Electron — unchanged Backend: Go daemon on :3001
⚠️ Disclaimer: This document is primarily focused on defining interfaces and service boundaries. Implementation details, data models, and internal wiring are intentionally deferred — the goal right now is to agree on the shape of the system before writing any code.

This document covers the design decisions and implementation plan for rewriting the AO backend in Go. The Go daemon runs as a subprocess spawned by the Electron main process, serving the REST API, SSE event push, terminal WebSocket, and the frontend static bundle — all on a single port. The frontend (TypeScript / Electron) is unchanged; only the backend changes.

What changes

Today AO runs a Next.js server (API routes + 2 WebSocket servers) alongside the lifecycle manager. The rewrite collapses this into a single Go binary with clear internal service boundaries. The frontend stays TypeScript/Electron — only the backend changes.

Key decisions

HTTP Framework

Settled
chi
http.Handler-compatible — WS upgrade is a zero-change drop-in. Subrouters let us apply different middleware stacks per surface. gin/fiber have custom contexts that fight with WS libraries.

Single Port

Settled
localhost:3001 — REST + SSE + WS + static
Local daemon, single user. Same-origin means no CORS. One lifecycle to drain on shutdown. Dev and prod are the same port. Six structural disciplines keep a future split cheap.

Event Push Transport

In Progress
SSE for state updates, WS only for terminal
Transport direction agreed — SSE is one-way, HTTP-native, has built-in EventSource reconnect. Full design (subscription model, frontend integration, envelope) still being finalised.

Port Conflict

Settled
Fail fast — clear error message
If port 3001 is taken, exit immediately. User configures a different port. Actual bound port written to running.json — that's how CLI and Electron discover it.

Route Surface

Settled
25 routes — exact path parity with current TS, under /api/v1
Rewrite, not reimagine. All 25 current routes preserved with identical paths and query-param contracts. Routes whose internals are unknown ship as no-ops. No pagination added. Consolidation comes in v2.

Graceful shutdown
1
Stop accepting. Signal handler fires on SIGTERM or SIGINT via signal.NotifyContext.
2
Close SSE connections. Drop open streams. Frontend's EventSource auto-reconnects and fails gracefully.
3
Drain HTTP. http.Server.Shutdown(ctx) — waits for in-flight REST requests to complete.
4
Lifecycle cleanup. Terminate running agent sessions. Write last-stop state.
5
Unregister. Remove entry from running.json.
6
Exit 0. Hard timeout: 10s total (matches current TS). If not clean, os.Exit(1).

Implementation plan
1
Phase 1 — Backend server running
4 sub-phases · can start immediately
1a
Skeleton
Daemon starts, binds port, shuts down cleanly. No routes yet.
  • go mod init — project structure: cmd/daemon/main.go, internal/server/, internal/config/
  • Config loading — port (default 3001), bind address
  • 127.0.0.1 bind + fail-fast on port conflict with clear error
  • Write PID + port to running.json on start; stale PID check on startup
  • chi router + 5-middleware stack wired per subrouter
  • signal.NotifyContext — SIGTERM + SIGINT → 10s graceful shutdown sequence
  • GET /healthz and GET /readyz
go run ./cmd/daemon starts, logs "listening on 127.0.0.1:3001", /healthz returns 200, Ctrl+C shuts down cleanly and removes running.json.
1b
Route shell
All 25 routes registered. No 404s anywhere. No logic yet.
  • /api/v1 chi subrouter mounted with correct middleware stack
  • All 25 routes registered with correct HTTP methods — handlers return 501 Not Implemented
  • No-op routes explicitly marked in code with a comment
  • GET /api/v1/events and GET /mux registered as placeholders (501)
curl localhost:3001/api/v1/sessions returns 501, not 404. Every current TS route has a corresponding Go route.
1c
Electron integration
Electron spawns and supervises the Go daemon. Frontend loads from the binary.
  • Spawn — Electron main process spawns ./ao-daemon as a child process on app launch
  • Discovery — main reads running.json to get the port; polls /healthz before allowing renderer to connect
  • Teardown — on app quit, main sends SIGTERM to daemon and waits up to 10s
  • Static serving — serve compiled frontend bundle via embed.FS with correct Cache-Control headers
  • Dev mode proxy — Next.js dev server on :3000 proxies /api/*, /events, /mux to Go on :3001
  • Packaged build — Go binary bundled via extraResources; embed.FS serves frontend; single-port verified
Packaged Electron app launches daemon, frontend loads from binary, /healthz gate prevents early connection. Dev mode (Next.js HMR + Go API) verified.
2
EventBus + SSE + Frontend subscription
Backend emits events over SSE. Frontend subscribes via a Context Provider and stores state in slices.
Backend — Go
  • Define Go event structs derived from what lifecycle manager actually emits
  • EventBus interface: Publish(topic, payload) + Subscribe(topics) (<-chan Event, unsubscribe func())
  • In-process implementation — goroutine fan-out, ring buffer ~1000 events, monotonic id: counter
  • SSE handler GET /api/v1/events?topics=sessions,prs,ci — reads bus, writes event: / id: / data: frames, heartbeat : ping every 15s
  • Per-resource scoped stream GET /api/v1/sessions/:id/events for detail pages
  • Wire lifecycle manager + SCM poller → EventBus.Publish()
Frontend — TypeScript / React
  • EventSourceContext — a React Context Provider mounted at app root. Opens one EventSource to /api/v1/events?topics=sessions,prs,ci. Manages connect / reconnect lifecycle (closes on unmount, re-opens on focus after backgrounding).
  • Event dispatch — provider listens to named events (addEventListener('session.updated', …)). On each event, calls the relevant Zustand/reducer action to update the matching store slice — no global re-renders.
  • Store slices — useSessionStore, usePRStore, useCIStore. Each slice has a patch(event) action that merges the SSE payload. Slices are initialised by REST (page load) and kept live by SSE.
  • Consumer hooks — useSessionEvents(id), usePREvents(id) subscribe to the scoped per-resource stream when a detail page mounts. Unsubscribe on unmount.
  • Connection status — context exposes status: 'connecting' | 'open' | 'closed' so components can show a stale-data indicator when SSE is offline.
// Provider (app root)
<EventSourceProvider topics={['sessions','prs','ci']}>
  <App />
</EventSourceProvider>

// Consumer (any component)
const sessions = useSessionStore(s => s.sessions)
const status  = useEventSource().status  // 'open' | 'connecting' | 'closed'
Open /api/v1/events?topics=sessions in the browser, spawn a session via REST, see event: session.updated arrive. In the app, the sessions list updates without a page reload.
Event taxonomy (which events each topic emits, exact payload shapes) must be agreed before wiring frontend dispatch.
3
Core routes
Routes the frontend actually uses work end-to-end. Highest-traffic first.
  • Sessions — GET /sessions (with ?project, ?active, ?orchestratorOnly, ?fresh), detail, spawn, kill, message, send, restore
  • Projects — list, detail, reload
  • Issues, backlog, PRs — GET /issues, GET /backlog, POST /prs/:id/merge
  • Meta — GET /version, POST /update, POST /webhooks/*
  • Unclear routes stay explicit no-ops — /remap, /patches, /orchestrators, /observability, /verify, /setup-labels
Kanban loads, sessions list renders, spawn + kill work. Full frontend feature-parity with current TS on the happy path.
4
WebSocket /mux
Bidirectional terminal streaming between frontend and agent sessions.
  • One WS connection per terminal session using coder/websocket
  • PTY framing — raw bytes upstream (keystrokes), raw bytes downstream (output)
  • Reconnect handling — client reconnects with session ID, server resumes stream
  • Lifecycle tie-in — clean WS close when underlying session terminates
  • Backpressure — slow client doesn't block other sessions
Terminal in Electron connects to /mux?session=:id, keystrokes reach the agent, output streams back in real time.
WebSocket design not yet complete — start that discussion before implementing.
