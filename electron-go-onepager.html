Next.js → Electron + Go: Migration One-Pager

A backend-engineer-friendly explainer of what changes when we move the frontend off the browser and into a desktop shell, with a Go service replacing the Node backend.

Today: Next.js (App Router) + Node Tomorrow: Electron + Go

1. What is Electron — and why will it help?

Electron is a runtime that packages a web app as a native desktop app. It is Chromium (the browser engine) plus Node.js, bundled into a single installable binary. Users double-click an icon; under the hood they get our React UI rendered in a Chromium window.

The two-process model

  • Main process — a Node.js process. Boots the app, creates windows, owns OS-level capabilities (filesystem, child processes, native menus, tray, auto-update). One per app.
  • Renderer process — a Chromium window. Runs our React tree exactly like it does in the browser today. Sandboxed: no direct OS access. One per window.
  • IPC bridge — the only sanctioned way the two communicate. The main process exposes a typed surface to the renderer via a preload.ts script.

Why it helps

  • Distribution. Ship a signed installer instead of requiring users to run a CLI / dev server.
  • OS integration. Native menus, system tray, notifications, deep links, file picker, auto-update — things browsers refuse to grant.
  • Local-first. We can spawn and supervise local processes (agents, tmux sessions, the Go service itself) without a running server.
  • Single trust boundary. Everything runs on the user's machine. No CORS, no auth tokens to ship, no public URL.

2. What is Go — and why will it help?

Go is a statically typed, compiled language with first-class concurrency. It produces a single static binary per platform, no runtime to install. It is the workhorse language for CLIs, daemons, and infra services for exactly the reasons we'd want it here.

Why it helps for this product

  • Process supervision is the core workload. Spawning agents, killing trees, watching tmux/PTY processes — this is what Go's os/exec and goroutine model are good at.
  • Concurrency. A goroutine per session is cheap. The current TypeScript backend juggles polling loops; Go expresses the same logic in far less code with channels.
  • One binary, three OSes. Cross-compile to macOS / Linux / Windows. No Node version skew, no node_modules, no native-module rebuilds.
  • Static types & tooling. Stronger guarantees than TypeScript at runtime (no any escape hatch), with a fast compiler and excellent stdlib for HTTP / JSON / fs.
  • Resource footprint. Lower memory and startup time than a long-running Node process — matters because it runs on the user's laptop alongside Electron.

3. How Electron and Go fit together

The Go service runs as a sidecar child process launched and supervised by the Electron main process. The renderer never talks to Go directly; it talks to main via IPC, which forwards calls to Go over HTTP + WebSocket bound to 127.0.0.1 (no gRPC).

What lives where

ComponentProcessResponsibility
Renderer Chromium window (sandboxed) React tree, UI state. Calls window.ao.*. No OS access.
preload.ts Runs inside renderer, before page JS The whitelist. Defines exactly which calls the UI is allowed to make.
Main process Node.js (privileged) App lifecycle, windows, IPC handlers. Spawns & supervises Go. Forwards IPC calls into HTTP/WS calls to Go.
Go sidecar Separate OS process All business logic. Bound to 127.0.0.1:<ephemeral port>. Same Go service code as a future remote deployment.

Why sidecar (vs. alternatives we considered)

PatternVerdict
Sidecar process (chosen) Clean boundary, easy to test, portable to remote later.
Embed backend in main process (Node rewrite) Throws away Go's value; couples UI & backend crash domains.
Native bindings (CGO / N-API) Hard packaging, hard debugging, async Go doesn't translate cleanly.
Go → WASM in renderer Can't spawn processes or access FS — non-starter for our workload.
Pure-Go desktop (Wails / Tauri) Viable but different framework; tracked separately, not part of this migration.

Concerns & guardrails for spawning Go from Node

RiskGuardrail
Orphan Go process if Electron crashes PID file on spawn; kill stale process on next launch before binding. (Already the pattern in running.json.)
Port collisions / hardcoded ports Go binds :0 (ephemeral), prints chosen port on stdout; main reads it before letting renderer connect.
Renderer calls Go before it's ready Main queues IPC calls until a health-check passes; main exposes a status field the UI can read.
Stdout/stderr backpressure deadlocks Go Always consume both streams in main — pipe into the logger.
Cross-platform process teardown (Windows ≠ POSIX) Use existing killProcessTree() from @aoagents/ao-core.
Packaging / code signing Bundle Go binary per OS/arch via extraResources; sign the embedded binary as part of macOS notarization.
Designing today so a future remote-Go is a config change, not a rewrite:
  • Renderer never knows where Go runs — only main does. Keep window.ao.* location-agnostic.
  • Go endpoint is a config value (e.g. AO_BACKEND_URL), not a constant. Local mode auto-picks an ephemeral port; remote mode reads a URL.
  • HTTP + WebSocket, not stdio. Stdio works only locally. HTTP/WS crosses machines unchanged.
  • Decide early: when Go moves remote, where do worktrees live? If they must stay on the user's machine, Go can't be fully remote without a sync story. Don't bake shared-filesystem assumptions into the API.
